数据中心利用率与资源优化 Streamlit Demo 项目 Summary for AI（新版）

一、项目定位

这个项目是 EOE（Energy Optimization Engine）中的“模块2：利用率与资源优化模块”。

用户正在开发一个面向数据中心和高能耗数字基础设施的作品集型 Streamlit demo，用于求职展示。这个 demo 的目标不是成为真实数据中心运维系统，而是作为个人作品集的一部分，展示用户具备“数据中心能耗分析、资源利用率优化、节能经济性评估、管理决策输出”的产品化能力。

核心展示逻辑：

上传资产利用率数据 CSV
→ 识别低利用率资产和疑似僵尸资产
→ 估算隐性能耗浪费和电费浪费
→ 估算资源整合、迁移、关停评估后的节能收益
→ 输出管理者和投资人能看懂的图表、KPI 和自动分析报告。

用户明确强调：
1. 不需要实时监控接口。
2. 不需要数据库。
3. 不需要真正服务真实数据中心。
4. 不需要复杂 SLA / 自动迁移 / 自动关停。
5. Demo 的目标是“能唬住企业管理者和投资人”，所以结果展示、逻辑自洽、页面专业感比真实运维复杂度更重要。
6. 用户不会 Python，只会复制粘贴、运行测试、反馈问题，所以后续回复要直接给可复制代码，不要讲太多专业实现细节。

用户后来提出：低利用率资产和疑似僵尸资产的定义不够清楚，页面上必须明确解释，否则别人会不理解“凭什么这样判断”。后续应在“模型说明”或类似折叠栏中加入定义：

低利用率资产：
分析周期内平均利用率低于设定阈值的资产。

疑似僵尸资产：
满足低利用率条件，同时活跃时段占比低于设定上限，并且未发现明显内存、磁盘 IO、网络 IO 活动，且不属于业务保护资产的资产。

候选资产：
疑似僵尸资产中，同时满足可迁移且非业务保护的资产。

同时要强调：
低利用率资产和疑似僵尸资产只是优先排查对象，不是自动关停对象。

核心公式：

资产功率 = 空闲功率 + (满载功率 - 空闲功率) × 利用率

输出包括：

avg_power_kw
peak_power_kw
cost
waste_energy_kwh
waste_cost
hourly_power

注意：当前代码中功率从 W 转 kW 的写法可能是先 /100 再 /10，等价于 /1000，结果正确但写法不优雅。可以后续顺手改成 /1000。

用户提出：
周期内的收益、支出金额对管理者意义不大，因为样本周期可能很短。后台变量可以保留，但页面和报告中不应重点显示“本周期省了几元 / 本周期花了几元”，应改为展示年度运营节省、一次性整合成本和首年净收益。

用户发现重要 bug：
当前年度净节省计算错误，表现为：
理论净节省为 -398，但年度净节省显示 -697,213。原因是系统把“周期净节省”乘以年化系数，而周期净节省中已经扣除了一次性迁移成本和风险成本，导致一次性成本被错误年化。

当前错误逻辑大概是：

周期净节省 = 周期运营节省 - 一次性成本
年度净节省 = 周期净节省 × 年化系数

这是错误的。

正确逻辑应该是：

周期运营节省 = 设备侧节省 + 冷却侧节省

一次性整合成本 = 迁移成本 + 风险成本

年度运营节省 = 周期运营节省 × 年化系数

首年净收益 = 年度运营节省 - 一次性整合成本

迁移成本和风险成本是一次性成本，不应该随着样本周期年化。

后续应在 core/consolidation.py 中修改公式，并建议输出新变量：

period_operating_saving
annual_operating_saving
one_time_consolidation_cost
first_year_net_benefit

原来的 gross_saving_cost、net_saving_cost、annual_net_saving 可以保留兼容，但页面上建议逐步改用新变量。

用户后来问整合率 50% 时后台如何决定哪些设备被整合。

当前整合决策逻辑如下：

第一步：筛候选资产
必须同时满足：
1. 疑似僵尸资产
2. migratable = Yes
3. business_critical = No

第二步：排序
增强模式下按：
risk_score 从高到低
avg_utilization 从低到高
energy_kwh 从高到低

基础/标准模式下按：
avg_utilization 从低到高
energy_kwh 从高到低

第三步：根据整合比例设定最多选择数量
例如候选资产 20 台，整合率 50%，则最多选择 floor(20 × 50%) = 10 台。

第四步：安全利用率约束
每加入一台候选资产，系统重新计算整合后平均利用率。如果超过安全上限，则不纳入。

结论：
当前逻辑是自洽的，可以保留。
但文案上 risk_score 容易误解为“迁移风险越高”，而实际上它更像“整合优先级评分”。后续建议把 risk_score 改名为：

中文：整合优先级评分
英文：Consolidation Priority Score

用户后来表示听不懂底层逻辑，只要现在逻辑自洽就行。因此短期可不改排序逻辑，只需要在页面文案上避免误解。

四、关于参数默认值的新判断

用户问：

1. 高负载阈值默认 40% 是不是太低？
结论：
如果叫“高负载阈值”，40% 偏低；
但实际逻辑是判断“是否明显活跃过”，所以应改名为“活跃利用率阈值”，默认 40% 可以保留。

2. 高负载时段占比阈值默认 5% 是不是太低？
结论：
如果理解为“高负载占比”可能困惑；
实际含义是“活跃时间太少就可能是闲置”，所以应改名为“活跃时段占比上限”，默认 5% 可以保留。

3. 默认空闲功率和满载功率是什么意思？
结论：
CSV 中如果有 power_idle 和 power_peak，就优先使用 CSV 的值。
左侧默认值只是 CSV 缺失时兜底。
因此应改名为“缺失时默认空闲功率 / 缺失时默认满载功率”。

4. 理论整合率是什么意思？
结论：
不是所有资产中有多少被整合，而是在“候选资产”中，有多少比例被纳入整合/下线评估。
应改名为“候选资产整合比例”。

5. 整合后安全利用率上限默认 65% 是否太低？
结论：
65% 不低，比较保守。
为了 demo 展示和管理者理解，可以调到 70%。
不建议默认 80% 以上，太激进。

6. 理论整合率默认 100% 是否更符合实际？
结论：
不建议默认 100%。虽然部分虚拟化环境中很多资源可以迁移，但现实中有业务保护、许可证绑定、固定 IP、备份、监控、低频任务、不可迁移资产等限制。
默认 70% 更稳，可允许用户手动调到 100%。

建议默认值：

低利用率阈值：10%
活跃利用率阈值：40%
活跃时段占比上限：5%
候选资产整合比例：70%
整合后目标利用率上限：70%
冷却节能折算系数：0.30
迁移成本情景系数：1.0
风险成本情景系数：1.0

模板中 migration_cost 和 restart_risk_cost：默认 0


五、关于迁移成本和风险成本的新判断

用户认为：
实际数据中心中迁移可能不花钱，只要不把设备弄坏就没有风险成本。

反馈结论：
用户直觉基本正确，尤其对于虚拟机/容器迁移，直接现金成本可能接近 0。
迁移成本更多是人工、排期、验证、回滚预案等隐性成本。
风险成本不是设备损坏成本，而是业务中断、数据不一致、服务异常、回滚失败等潜在风险的抽象估算。

因此在 demo 中：

模板默认 migration_cost = 0
模板默认 restart_risk_cost = 0

左侧保留：
迁移成本情景系数
风险成本情景系数

但作为保守情景调节项，不是必填项。

如果用户没有明确成本数据，建议默认 0。
